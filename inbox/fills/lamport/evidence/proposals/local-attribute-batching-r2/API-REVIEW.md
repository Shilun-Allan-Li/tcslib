# Source-only batching proposal

This proposal changes only the probe generator's `seal_command`; the source proof, active generator, active queue, selection rules, controls and manifests are untouched. `prepare_seals_candidate.py` is Python-AST checked and its pure generator has been compared with the original on empty, three-name and full 1,438-name requests, for both INSTALL and EOF. It has **not** been Lean-compiled or benchmarked. `proposal.patch` is the complete proposed delta. The earlier r1 proposal is preserved as an uncompiled draft with a generated-string escaping issue; use r2 only.

The candidate runs each entire INSTALL/EOF validation loop in one `Lean.Elab.Command.liftCoreM`. INSTALL resolves `Lean.getAttributeImpl env `irreducible` once, then invokes the registered handler's `add n Lean.Syntax.missing .local` under `Lean.withExporting (isExporting := false)`. It preserves the exact actual-Name catalog, definition/home/uniqueness validation, already-irreducible skip, final status assertion, per-name INSTALL/EOF rows and total count checks. It does not use any raw reducibility setter, global attribute, or unsafe option. Request selection and all six controls are unchanged.

Pinned Lean4.25 source evidence:

- `Lean/Elab/Declaration.lean:300–334`: the ordinary attribute command elaborates attributes once, but then invokes `liftTermElabM` for **each** identifier before `Term.applyAttributes`. A single multi-identifier command therefore keeps those per-name Term/Meta state crossings.
- `Lean/Elab/Command.lean:689–706`: each Term lift calls `withSaveInfoContext`, constructs a fresh Term/Meta run, and runs a Core action. `runCore` at163–208 synchronizes command/environment/info/message state. Eliminating repeated lifts is a plausible performance improvement, not yet a measured one.
- `Lean/Elab/Term/TermElabM.lean:927–970`: `applyAttributesCore` obtains the current registered implementation, wraps local application with `withExporting false`, and invokes `attrImpl.add declName attr.stx attr.kind`. Its other wrappers provide declaration/message/info context rather than reducibility behavior.
- `Lean/Attributes.lean:20`: `AttrM` is `CoreM`. `getAttributeImpl` at487 is public; the default kind of `Attribute.add` at501 is GLOBAL, so this proposal explicitly passes `.local` to the implementation. `Attribute.Builtin.ensureNoArgs` at87–94 explicitly accepts `Syntax.missing`.
- `Lean/ReducibilityAttrs.lean:102–139`: the registered irreducible handler still runs `validate` and then applies the chosen attribute kind in the current namespace. Local updates go through `reducibilityExtraExt.addCore` at71. The public setters at173/193 force GLOBAL semantics and are intentionally unused.
- `Lean/Environment.lean:2691–2700`: `withExporting false` restores only the exporting flag after application while retaining environment updates. The Core lift receives the command scope's current namespace/options from `Command.runCore`, preserving the global-prefix/file-local attribute scope used by the old generator.

Observable differences on *invalid* inputs: direct handler exceptions propagate immediately instead of first passing through Term's `withLogging`; the harness still fails closed with missing completion markers, so this cannot accept an invalid seal. One Core heartbeat context replaces many fresh ones; the harness already uses `maxHeartbeats 0`. IDE/info-tree contexts are reduced. The handler itself needs no omitted Term/metavariable context.

Before deployment, use a fresh required guarded module-check attempt for one 1,438-name Reader control, verify exact payload/home/status/INSTALL+EOF coverage and output, then run fresh full Planted A/B plus six controls. Record native time/RSS and keep the old attempts. A strong speed gain plus identical successful control coverage would justify versioning the remaining queue at a graceful phase boundary; otherwise continue the existing stable generator.
