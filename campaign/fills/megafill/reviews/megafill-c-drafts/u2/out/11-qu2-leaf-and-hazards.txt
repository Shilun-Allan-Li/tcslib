# 11 — Q-U2: the header-ruler leaf; copy hazards for the leaf and for the suffix drop

## House rules for a private leaf
- policy.md, Construction reuse: "A hand-built machine is acceptable only when no layer covers the
  need, and its docstring must say so and name what was missing". Hosts come first: leaf rows
  (copy, compare, seek, arithmetic) are not hosts. A finite-state pair scan that writes one ruler
  cell per header cell is a leaf. It drives no routine and its contract fits its consumer.
- Precedents: startup-cont1 authorized one input-rewind leaf (rule 7) and its review accepted an
  unlisted one-step leaf (F1, "none of the banned kinds"). configclock-cont2 lists its leaves
  ("cw_leftTM and a one-step exit dispatch … Nothing else"). H5's own rd_test is a private leaf
  with the docstring sentence "No catalog row moves the input head together with a work head".
  The draft does the same: exactly one leaf, a docstring naming the gap, any further leaf an
  escalation. Within the rules.
- No public row writes a header-length ruler. Search of the tree and of #156/#135's heads: the
  'ruler' hits are G4's lockstep walk (walkTM, the ruler is a work-tape word),
  ExhaustiveReplay's pass, ZoneRebalance's zone ruler, RAMSimulation's width ruler, H5's
  device/host (consumers of the ruler), and Hierarchy's sorried space_universal (the second
  consumer). InputDevice's rd_test docstring confirms that no catalog row moves the input head
  with a work head. LogProg's scanR (SpaceComplexity/Machines/ParsePlain) is a register-program
  scan, another machine layer, and writes nothing.

## "Publish at its second consumer"
Right for a leaf, and consistent with "a private host already in the tree is harvested into the
shared layer before a second consumer is briefed against it". space_universal's docstring
(Hierarchy.lean:115–122) needs the same scan over a two-pairing header,
ℓ = 2|bits s| + 2|α| + 4, ending at ℓ + 1. Two runs of a one-header scan give that, if the run
lemma is stated generically:
- from input position 1 + p, with z.drop p = pairEncode u v;
- with the ruler head at r over blank cells;
- writing true at r, …, r + 2|u| + 1;
- ending at input 1 + p + 2|u| + 2 and ruler head r + 2|u| + 2.
U2-E is then the instance p = 0, r = 0. Recommend that the brief ask for that form (no extra
public surface; the promotion becomes a visibility change).

## Copy hazards the draft does not name (would-be copies of what the route needs)
- The leaf's run lemma reads header cells of pairEncode α x. UniversalStartup's private
  universal_pair_get ((pairEncode α x)[2j]? = some α[j], and [2j+1]?) and
  universal_pair_separator read exactly these cells. So does its prefix parser's run
  (universalPrefixCfg, universalPrefix_step, universalPrefix_bits): the same aligned-pair scan
  without the ruler write. UniversalStartup is in the population, so a transcription shows as a
  new cross-file pair. The public SpaceComplexity/Logspace/InputAccess.pairEncode_getD has the
  same content outside the closure and outside the population. Suggest reading by a suffix
  invariant: inputSymbolInner, List.getElem_drop, and pairEncode (b :: β) x = b :: b :: pairEncode β x
  from pairEncode_eq. Name the three privates as hazards, and add InputAccess to the population.
- The ruler host needs (pairEncode α x).drop (2|α| + 2) = x. No lemma in the closure states it.
  It is NDCodeSimulator's private ic_input_suffix (in the population), the local hd inside
  InputDevice's public pairEncode_pairEncode_drop, PathWalk's private drop_pairEncode, and
  Codec/Parse's public pe_drop (not imported). A uk_ copy is a fifth member and a new cross-file
  pair, which the brief forbids with nothing pre-disclosed (F2). Fix: publish
  Turing.pairEncode_drop in InputDevice with the Q-U1 PR (same replay closure; 07 proves it and
  re-points pairEncode_pairEncode_drop), and ledger the family for the dedup window
  (ic_input_suffix, drop_pairEncode, pe_drop re-pointed later). Or pre-disclose one uk_ copy.
